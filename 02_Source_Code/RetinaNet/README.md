# FreshScan AI — Fruit & Vegetable Detection (RetinaNet, transfer learning)

An object detection system that finds fruits and vegetables in a photo,
draws a bounding box around each one, and labels it — powered by
**RetinaNet (ResNet50 backbone + Feature Pyramid Network)**, starting from
ImageNet/COCO-pretrained weights and fine-tuned on the same LVIS Fruits &
Vegetables dataset used by the earlier custom-CNN project.

> This project uses `torchvision`'s built-in RetinaNet implementation
> (pretrained backbone + FPN + Focal Loss, all standard components from
> the original RetinaNet paper), fine-tuned for this dataset's 63
> classes — it is NOT trained from scratch. This is intentional: it's
> meant to sit alongside a from-scratch custom CNN and a YOLO model in a
> group comparison, illustrating the difference transfer learning + a
> mature multi-scale architecture makes versus training a simple grid
> detector from zero.
>
> The anchor sizes have also been customized for this dataset (see
> `model.py`) — this dataset's objects run noticeably smaller than
> COCO's (median ground-truth box size is ~25px, with a long tail down
> to under 10px), so the default RetinaNet anchor range doesn't cover
> them well out of the box. Anchors are scaled ~1.33x relative to a
> 480/640 baseline, matching this project's actual `MIN_SIZE`/`MAX_SIZE`
> (640/800) — if those resize dimensions ever change, the anchor sizes
> in `model.py` need to be rescaled to match, or small objects will
> stop lining up with the anchors meant to catch them.
>
> Training also uses a **per-class weighted focal loss**
> (`WeightedRetinaNetClassificationHead` in `model.py`) — rare classes
> get up-weighted so the loss isn't dominated by whichever fruit/veg
> happens to have the most boxes in the dataset. Weights are
> precomputed once via `compute_class_weights.py` and loaded from
> `class_weights.pt` at model build time (falls back to uniform
> weights with a warning if that file doesn't exist yet).
>
> Training data augmentation also includes a small-object-aware zoom
> crop and oversampling of images containing small objects (see
> `dataset_utils.py`) — a large share of this dataset's objects are
> small enough that they retain very little pixel information after
> the model's internal resize, so these two changes were added to give
> the model more, and better-quality, exposure to them during training.

## 1. Project structure

```
RetinaNet/
├── app.py                       # Flask web app (upload photo -> boxes + labels + metrics)
├── train.py                     # Trains RetinaNet: new / resume / warm-start runs, logs metrics
├── evaluate.py                  # Re-scores an already trained run at the current threshold
├── sweep.py                     # Sweeps SCORE_THRESHOLD on one run's best checkpoint, reports best F1
├── compute_class_weights.py     # Scans training labels, writes class_weights.pt for model.py
├── run_manager.py                # Tracks each training run's own folder + completion status
├── model.py                       # Builds pretrained RetinaNet, custom anchors, weighted head
├── dataset_utils.py                 # YOLO-format annotations -> PyTorch Dataset, incl.
│                                       augmentation (random crop, small-object zoom crop,
│                                       flip, color jitter) and small-object oversampling
├── metrics_utils.py                   # IoU matching, evaluation metrics, results log
├── inference.py                         # Runs the model on one photo, draws boxes
├── config.py                             # All paths & hyper-parameters in one place
├── classes.txt                            # One class name per line (same as the CNN project)
├── class_weights.pt                        # Generated by compute_class_weights.py (not in git)
├── requirements.txt
├── scripts/
│   └── generate_classes.py                   # Builds classes.txt from the dataset's data.yaml
├── runs/                                       # Every training run, one folder each (runtime)
│   └── run_2026-08-16_10-30-00/
│       ├── retinanet.pt                           # latest checkpoint (crash-safe resume)
│       ├── retinanet_best.pt                       # best checkpoint (used for eval/app/warm-start)
│       ├── training_log.csv                         # one row per completed epoch
│       ├── training_history.json                     # written only when the run finishes
│       └── COMPLETED                                   # empty marker, written only on success
├── results/
│   └── model_comparison.json                            # Recorded metrics, shared with other algorithms
└── data/                                                  # Dataset goes here (see step 4)
```

## 2. Prerequisites

- Python **3.10 or 3.11**
- An NVIDIA GPU with CUDA is **strongly recommended**. RetinaNet +
  ResNet50 is much heavier than the earlier from-scratch CNN — on CPU,
  a single epoch can take 20-30+ minutes; on a modest CUDA GPU it's
  usually a couple of minutes. Lower `BATCH_SIZE` in `config.py` if
  you're on a smaller GPU (4-6 GB VRAM).
- ~2 GB free disk space for the pretrained weights (downloaded
  automatically on first run) + the dataset

```bash
python3 -m venv venv
```

> Run `deactivate` to leave it.

### GPU (CUDA) setup — do this before training

`pip install -r requirements.txt` by itself will usually install the
**CPU-only** build of PyTorch. To actually use your GPU:

```powershell
# check your GPU + driver are visible first
nvidia-smi

# uninstall the CPU-only build, then install the CUDA build
# (pick the right cu### tag for your setup at pytorch.org/get-started/locally)
pip uninstall torch torchvision -y
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu121
```

Verify it worked:

```powershell
python -c "import torch; print(torch.__version__); print(torch.cuda.is_available())"
```

This should print a version ending in `+cu###` (not `+cpu`) and
`True`. `train.py` auto-detects CUDA (see `get_device()` in
`train.py`, controlled by `config.DEVICE`) — no code changes needed
once torch itself is installed correctly.

**Monitoring GPU usage while training** — open a separate PowerShell
window (not the one running `train.py`) and run either:

```powershell
while ($true) { cls; nvidia-smi; Start-Sleep -Seconds 1 }
```

or, for a nicer live dashboard:

```powershell
pip install nvitop
nvitop
```

## 4. Reuse the same dataset as the CNN project

This project expects the **exact same** dataset layout as the earlier
custom-CNN project:

```
RetinaNet/
└── data/
    └── LVIS_Fruits_And_Vegetables/
        ├── data.yaml
        ├── images/{train,val,test}/...
        └── labels/{train,val,test}/...
```

Easiest option: **copy** (or symlink) the `data/LVIS_Fruits_And_Vegetables/`
folder from your CNN project into this project's `data/` folder — no
re-downloading needed, the format is identical (YOLO-format `.txt`
annotations).

Also copy your existing `classes.txt` from the CNN project into this
project's root, or regenerate it:

```bash
python scripts/generate_classes.py
```

### Class weights (recommended before your first real training run)

```bash
python compute_class_weights.py
```

Scans `TRAIN_LABELS_DIR`, counts boxes per class, and writes
`class_weights.pt` — `model.py` loads this automatically at build time
and feeds it into the classification loss so rare classes aren't
drowned out. If this file doesn't exist, training still runs, but
`model.py` prints a warning and falls back to uniform (unweighted)
class loss.

## 5. Train (fine-tune) the model

```bash
python train.py
```

A menu lets you resume an unfinished run or start a new one:

```
===== RetinaNet Training Runs =====
Unfinished runs found:
  [1] run_2026-08-16_10-30-00 - 4 epoch(s) completed (checkpoint saved)
  [2] Start a NEW model run
Select a run to continue, or 2 for a new run:
```

- **Resuming** reloads that run's saved checkpoint (model weights,
  optimizer state incl. AdamW momentum, scheduler state, epoch count,
  early-stopping counter, and training history) and continues from the
  last completed epoch.
- **Starting a new run** downloads the pretrained RetinaNet weights
  (first time only, needs internet access) and fine-tunes from there —
  unless you also pass `--warm-start-from` (see below).

Non-interactive flags (handy for scripting or restarting after a crash):

```bash
python train.py --new --run-name my_run --epochs 20 --batch-size 4 --lr 0.0001
python train.py --resume my_run --epochs 30
```

If you're on CPU or a small GPU, lower `--batch-size` (e.g. to 2) first.

### Warm-starting a new run from a previous run's weights

Instead of starting from ImageNet-pretrained weights, a new run can
start from another run's **best** checkpoint — useful after a change
to the model (e.g. the weighted classification head) that keeps most
of the architecture compatible but shouldn't inherit the old
optimizer/scheduler state:

```bash
python train.py --new --run-name model_V9 --warm-start-from model_V8
```

This loads `model_state_dict` from `runs/model_V8/retinanet_best.pt`
with `strict=False` (any new/renamed submodules, like the classification
head's `class_weights` buffer, are simply skipped — everything else:
backbone, FPN, box regression head, and the classification head's conv
layers, still loads normally). The optimizer and scheduler always start
**fresh** for a warm-started run, same as any other new run — this
avoids inheriting a learning rate that `ReduceLROnPlateau` may have
already decayed close to `min_lr` on the old run. `--warm-start-from`
only takes effect when starting a new run; it's ignored with `--resume`.
The run's checkpoint records which run it was warm-started from
(`warm_started_from` field), so this stays traceable later.

### What each epoch does

1. The backbone (ResNet50) stays **frozen** for the first
   `FREEZE_BACKBONE_EPOCHS` epochs of a fresh run (default 5), so the
   randomly-initialized new classification head doesn't send destructive
   gradients into the pretrained features before it's learned anything.
   After that, the whole network fine-tunes together. This warmup is
   based on the actual epoch number, so it also applies correctly after
   a resume.
2. The optimizer uses **two learning-rate groups**: the backbone trains
   at `0.1x` the head's learning rate, since it starts from pretrained
   (or warm-started) weights and shouldn't be pushed around as
   aggressively as the head. Both rates are logged every epoch
   (`backbone_lr` / `head_lr`) and stepped together by the
   `ReduceLROnPlateau` scheduler.
3. Training images are augmented (random resized crop, a small-object
   zoom crop when the image has a small object, horizontal flip, color
   jitter — see `dataset_utils.py`) to reduce overfitting and give small
   objects more effective resolution during training; validation images
   are not augmented. Images containing small objects are also
   oversampled via a `WeightedRandomSampler`, so the model sees them
   more often per epoch without any ground-truth boxes being discarded.
4. Trains one pass over the training set, evaluates validation loss.
5. Saves a **latest** checkpoint every epoch (crash-safe resume, full
   optimizer/scheduler state included) and, whenever the model
   improves, a separate, smaller **best** checkpoint (model weights
   only) — this is the one used for the final evaluation, `evaluate.py`,
   `sweep.py`, `--warm-start-from`, and the apps.
6. **How "improved" is decided**: for most of training this is just
   `val_loss` getting lower. For the **last `F1_EVAL_LAST_N_EPOCHS`
   epochs** (default 15), each epoch instead runs a full detection pass
   (real inference + NMS + IoU matching, filtered at `SCORE_THRESHOLD`)
   and compares `objectness_f1` — since `val_loss` doesn't always track
   detection quality once the model is close to converged, the true
   optimum near the end of training is chosen by F1 instead. The best
   checkpoint records `saved_because: "val_loss"` or `"F1"` so you can
   tell which criterion picked it.
7. Stops early if the run hasn't improved (by whichever criterion was
   active that epoch) for `EARLY_STOP_PATIENCE` epochs in a row
   (default 10).
8. Once finished, reloads the **best** checkpoint and runs a full
   evaluation on the validation set (predictions filtered at
   `SCORE_THRESHOLD` first — see the note below), logging metrics to
   `results/model_comparison.json`.

> **Note:** `val_loss` and the final detection metrics (recall, f1,
> etc.) are not directly comparable to each other — `val_loss` is a
> training-mode loss computed with ground truth forced in, while the
> final metrics come from real inference (score threshold + NMS). A
> lower val_loss does not guarantee a better detection score; use the
> final `[train] Validation metrics:` block (or `evaluate.py`) as the
> real measure of quality.
>
> **Note on thresholds:** the model itself is built with a very low
> internal `score_thresh` (0.01) so it returns essentially every
> candidate detection above noise level. `train.py`'s final evaluation
> and `evaluate.py` then explicitly filter those predictions down to
> `SCORE_THRESHOLD` (`config.py`, default 0.35) before scoring — this
> keeps the "which confidence cutoff counts as a detection" decision in
> one place (`config.py`) rather than baked into the model, so it can
> be changed and re-evaluated without retraining. Run `sweep.py` (below)
> to find the best threshold for a given trained model empirically.

## 6. Re-evaluating without retraining

```bash
python evaluate.py                          # evaluates the latest completed run
python evaluate.py --run RUN_NAME            # evaluates a specific run
python evaluate.py --run RUN_NAME --score 0.3   # override the score threshold
```

Always loads `retinanet_best.pt`, never the latest-epoch checkpoint —
mixing which checkpoint gets loaded is what caused inconsistent,
non-comparable results in earlier evaluations. Handy after tweaking
`SCORE_THRESHOLD` / `NMS_IOU_THRESHOLD` in `config.py`, or after
training finishes. Each call logs an entry to
`results/model_comparison.json` (existing entries for the same model
name are replaced, not duplicated).

### Sweeping the score threshold

```bash
python sweep.py --run RUN_NAME   # defaults to the latest completed run
```

Runs inference **once** on the best checkpoint, then re-filters that
same set of predictions across a range of thresholds
(0.05 → 0.80), printing precision/recall/F1/classification-accuracy/
mean-IoU at each one and logging the best-F1 result to
`results/model_comparison.json`. Useful for picking a `SCORE_THRESHOLD`
without re-running the model over and over.

## 8. How the metrics are computed (for model comparison)

Unlike the earlier grid-based CNN (evaluated cell-by-cell), RetinaNet
outputs real, variable-count, already-NMS'd detections. Evaluation
matches each image's predictions against ground truth with greedy IoU
matching (see the docstring at the top of `metrics_utils.py` for the full
algorithm), producing the SAME metric names as the CNN project so both
sit in the same comparison table:

| Metric | Meaning |
|---|---|
| `objectness_precision` | Of all predicted boxes, how many matched a real object (IoU ≥ 0.5) |
| `objectness_recall` | Of all real objects, how many were matched by a prediction |
| `objectness_f1` | Harmonic mean of precision and recall |
| `classification_accuracy` | Among IoU-matched pairs, how often the predicted class is correct |
| `mean_iou` | Average IoU over all matched pairs |
| `detection_rate_at_iou_0.5` | Fraction of ground-truth objects detected with the right class AND IoU ≥ 0.5 |

This is simpler than full COCO mAP (no per-class average precision
curve), but stays consistent with the CNN project's schema for a fair
side-by-side comparison. Note that `objectness_precision`/`recall`/`f1`
are highly sensitive to `SCORE_THRESHOLD` — always report which
threshold a given result was measured at.

### Adding the other algorithms' results to the same table

Any teammate's results (YOLO, MobileNet, etc.) can be added to
`results/model_comparison.json` using the same schema so they show up
automatically in the web UI's comparison table — see the CNN project's
README for the exact JSON format.

## 9. Troubleshooting

- **`FileNotFoundError: No images found in ...`** — the dataset isn't in
  `data/LVIS_Fruits_And_Vegetables/` yet. See step 4.
- **`torch.cuda.is_available()` is `False`** — you likely have the
  CPU-only build of torch installed. See the GPU setup steps in Section 3.
- **Training is very slow / out of memory** — lower `BATCH_SIZE` in
  `config.py` (try 2), and/or lower `MIN_SIZE`/`MAX_SIZE`. You're likely
  on CPU or a small GPU. If you do lower/raise `MIN_SIZE`/`MAX_SIZE`,
  remember to rescale the anchor sizes in `model.py` to match (see the
  note at the top of this README) — otherwise the anchors and the
  actual object sizes after resize will no longer line up.
- **`[model] WARNING: class_weights.pt not found, using uniform
  weights`** — run `python compute_class_weights.py` first (see step 4).
  Training will still work without it, just without the per-class
  weighting.
- **A later epoch takes noticeably longer than the first couple** — this
  is expected: the backbone unfreezes after `FREEZE_BACKBONE_EPOCHS`
  (default epoch 6 onward), which increases both the backward-pass
  computation and the number of parameters the optimizer updates.
- **The last ~15 epochs are noticeably slower than earlier ones** — this
  is expected: those epochs also run a full detection evaluation pass
  (real inference + IoU matching), not just validation loss — see
  `F1_EVAL_LAST_N_EPOCHS` in `train.py`.
- **`--warm-start-from RUN_NAME` fails with a missing-checkpoint
  error** — that run has no `retinanet_best.pt` yet, meaning it never
  completed a single improving epoch. Let it train further, or pick a
  different run.
- **`objectness_precision` equals `objectness_accuracy` and both look
  very low** — this means predictions were scored without filtering by
  `SCORE_THRESHOLD` first. `evaluate.py`, `sweep.py`, and the end of
  `train.py` already call `filter_predictions_by_threshold(...)` before
  `evaluate_predictions(...)` — check that this hasn't been removed if
  you see this pattern.
- **Startup is slow / seems to hang the first time a run starts** —
  `FruitVegDetectionDataset.__init__` reads every training label file
  once to compute small-object oversampling weights; on the full
  dataset this can take a minute or two before any progress output
  appears. This is expected, not a hang.
- **`TypeError: RetinaNet() got multiple values for keyword argument
  'anchor_generator'`** — don't pass `anchor_generator` directly into
  `retinanet_resnet50_fpn_v2(...)`; build the model first, then set
  `model.anchor_generator = ...` afterward (see `model.py`).
- **"Model not ready" in the app** — no run under `runs/` has finished
  yet. Run `python train.py` and let it finish, or resume an unfinished
  run.
- **First run is slow to start** — the pretrained RetinaNet weights
  (~130 MB) download automatically the first time `build_model()` runs
  with `pretrained=True` (skipped entirely when warm-starting); this
  needs an internet connection once.
- **`ModuleNotFoundError`** — make sure the venv is activated (you should
  see `(venv)` in your terminal prompt) and `pip install -r
  requirements.txt` completed successfully.
